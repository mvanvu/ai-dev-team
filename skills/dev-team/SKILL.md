# Dev Team orchestrator

The main session is the **leader**. It profiles the repo, plans with the user, owns the task board, briefs the agents, merges their feedback and talks to the user (in the user's language). It never writes production code itself. All files the team writes are in English.

## Team

| Agent (`subagent_type`) | Model | Skills | Modes | Output |
|---|---|---|---|---|
| `developer` | opus (sonnet / fable per Model per role) | implementation; pwa-headless-ui and ui-ux-design for client tasks and UI design | implement (server or client task, per `Owner`), UI design, fix, bug | code + tests, `$TEAM_WS/04_dev_T{id}.md`, `$TEAM_WS/02_ui-spec.md` |
| `reviewer` | opus (sonnet for other-than-high-risk task reviews) | code-review-checklist; security-review-checklist; ui-ux-design (design QA) | review (code + security + design QA in one pass), threat model, final-review dimension, verify, full audit | verdicts, `$TEAM_WS/02_threat-model.md` |
| `qc` | sonnet | qa-verification | QC per task, sign-off | `$TEAM_WS/05_qc_report.md`, `$TEAM_WS/qa-artifacts/` |

The leader itself uses `project-profiling` (Phase 1), and for planning `superpowers:brainstorming` + `superpowers:writing-plans` when the `superpowers` plugin is installed in this session — otherwise `spec-writing` + `technical-design`. `technical-design` also holds the task-board format, default stack, toolchain and sizing rules the plan must meet either way.

The board's `Owner` column says which side a task is: `be` (server) or `fe` (client); the brief names it and loads only that side's skills. A task never mixes server and client code; server tasks are built, reviewed and QC'd before the client tasks that consume their contracts.

### Agent and skill names
Installed as the `ai-dev-team` plugin, agents and skills carry the `ai-dev-team:` prefix: `subagent_type: "ai-dev-team:developer"`, skills `ai-dev-team:<skill>`. If the agent list shows un-prefixed names (files copied into a project's `.claude/`), use those and pass `agentPrefix: ''` to the Phase 5 workflow.

## Routing by request type

| Request | Phases |
|---|---|
| **Small change** — a few files, no contract/schema/public-API change, no new screen ("quick fix", typo-level bug, small tweak) | 0 → 1 if no profile → one-row board → 4 (**light tier**: developer, then one reviewer; qc only when a criterion needs runtime proof) → 6 |
| Layout complaint on an existing screen (wasted space, broken or cramped layout) | 0 → 1 → `developer` in **UI design** mode (pack `DESIGN`) writes a short `$TEAM_WS/02_ui-spec.md` delta with the options as a mockup folder: the complaint with the sweep cells that show it, 1–3 layout options, and every conflict between rules (density vs touch-target size, truncation vs wrapping) → leader asks the user to pick when options differ in behavior → 4 (**light tier**; the reviewer's design QA on the sheets replaces qc) → 6 |
| Bug (non-trivial) | 0 → 1 → 2 (bug spec: repro, expected, `AC-n`) → 3 (board only, usually one or two rows) → 4 (the developer reproduces first on the side where the bug shows; a bug that needs server and client changes becomes a server row, then a client row) → 6; add 5 if the fix touches security |
| New feature / screen | 0 → 1 → 2 → 3 → 4 → 5 → 6 |
| New project (greenfield) | 0 → 1 → 2 → 3 (stack proposal, **user approves**) → 4 (scaffold task first, then **rerun 1** to profile the new commands, then the rest) → 5 → 6 |
| Review only ("review this branch", "security review", "audit") | 0 → 1 → 5 (`mode: 'review-only'`) → 6 |
| UI design only | 0 → 1 → 2 → 3 (developer in UI design mode only) → 6 |
| New template / theme pack | 0 → 1 → 2 (short) → 3 (developer UI design: tokens + recipes) → 4 (no core component edits) → 6 |
| PWA / Capacitor setup, mobile app | 0 → 1 → 2 → **mobile platform choice** → 3 → 4 → 5 (include `security`) → 6 |
| Continue / resume / follow-up | Phase 0 decides |

**One-line text fixes**: a finding that only asks to correct a line of documentation, a comment or user-facing copy (no code, config or behavior) is fixed by the leader directly and noted on the board; it needs no developer round-trip and no re-review.

**Docs-only task** (only documentation or notes change — no code, tests, assets, config or data): the leader spot-checks the notes and the diff against the code they describe instead of spawning a reviewer, sends a quick pass if something is wrong, and the task does not block sign-off or Phase 5. A doc that states behavior (API, commands, config keys) gets a sonnet reviewer.

**Lasting taste**: when the user states a look-and-feel preference that is not about one screen ("brighter colours", "less text"), the leader adds it to the profile's `design_taste` and says so in one line (`ai-dev-team:ui-ux-design` → `references/ease-of-use.md` §2).

**Light tier** (small change, layout complaint): developer + one reviewer, no qc unless a criterion needs runtime proof; light sweep (`references/resource-budget.md` §3); compliance table limited per `references/rule-packs.md` §6; no Phase 5. It never applies to a task that touches auth, permissions, payments, data deletion or a schema — those take the normal route.

When unsure whether a change is small, treat it as a bug route; when a "small change" grows past its limits during work, upgrade it to the bug route.

**Ambiguous words first**: when a word in the request names more than one thing in this repo or run ("template" = the plugin's profile template or the site template; "seed" = the mockup content set or the demo database; "the app" = web or mobile), ask one AskUserQuestion with each concrete reading as an option before any agent starts or any file changes. Stating the reading and starting anyway ("tell me if you meant otherwise") is not asking: the work done on the wrong reading is lost when the user answers.

**Request research** (new feature, new product, greenfield, or a plan of 4+ tasks): the leader first asks whether to research the request (header `Research`); only on a yes do 1–3 time-boxed lens agents study the repo and comparable products on the web in the background, and one synthesis agent turns that into 3–5 sourced options (core / expected / optional, one Recommended) for the user to pick from before the spec questions start — `references/request-research.md`, pack `RESEARCH`. On a no, Phase 2 runs as before.

## Resource budget
The budget lives in the project profile (`max_agents`, `max_verifiers`, the `run-heavy` wrapper, `ui_widths`, `ui_themes` — written in Phase 1) and, for this machine, `$TEAM_STATE/local.md` (`heavy_workers`, `heavy_slots`):
- **Concurrent agents: `max_agents` developers (default 4) plus `max_verifiers` reviewers and qc (default 4)**. Agents cost little local CPU — the commands they run do, and those are capped by `heavy_slots` — so a reviewer, qc, quick-pass re-check or research lens never waits for a developer slot. Developers (build, fix, quick pass, escalation) count against `max_agents`; reviewers, qc, research lenses and Workflow agents against `max_verifiers`. When a cap is reached, queue the next spawn of that kind. Priority: fix rounds, then review/QC of in-flight tasks, then light-tier tasks the user added during the run (a small change asked mid-build runs as soon as the current task is done, ahead of planned tasks), then other new tasks. Tell the user where a new task sits in the queue and roughly when it starts.
- Heavy commands (suites, builds, e2e, audits, browser launches) go through `$TEAM_BIN/run-heavy.sh`; it runs at most `heavy_slots` of them at a time machine-wide, so the leader does not schedule browser or test work by hand. Light commands (one test file, a small related run, lint of changed files) run directly (`references/resource-budget.md` §2). Before telling the user a heavy step is running, check `run-heavy.sh --status`: a command still waiting for a slot is reported as queued, with what holds the slot. The scripts are never copied into the project (`ai-dev-team:project-profiling` step 7).
- `COST` applies to every task and `SWEEP` to every task that changes a web screen — `references/resource-budget.md`: each check runs once by the agent that owns it, full width × theme sweep in one run per build, no `sleep`/`pgrep` polling, one sign-off qc with one full-suite run. A brief never raises these limits unless the user asked — and then the user hears the cost first.

## Environment work by the leader
Starting the app or demo, installing a package into it, seeding or resetting it is environment work, not production code; the leader may do it with the profile's `app_start` and the project's own scripts.
- **Diagnose briefly**: when it fails, at most ~3 diagnostic commands (the error, the log, `rule-checks.sh env-drift`); still unclear → an `env` task for a `developer` on `sonnet` with the error, the commands tried and the files involved, and the leader goes back to the board. Long debugging in the leader's own context slows every task waiting for a slot and fills the context that has to last the whole run.
- **Workaround vs bug**: a manual step that makes the environment work (running an install SQL by hand, recreating a container, copying keys into `.env`) is recorded in the profile's `## Environment issues` or the project's setup notes. When the cause may be a product defect that users would also hit (an installer that skips its tables on a re-install, a build that ships an incomplete package), add a `bug candidate` line to the board notes with the evidence and name it in the next message to the user; the user decides whether it becomes a bug task.
- **Shared toolchains once**: an SDK or tool version the project pins (a Flutter version in a script, a Node version in `.nvmrc`, a JDK) that this machine lacks is installed once by the leader or an `env` task, into `$TEAM_TOOLS`, before any task that needs it starts, and recorded in `$TEAM_STATE/local.md` (`tools`) and in the brief's commands. Developers never install one themselves (`BASE-17`): two agents installing the same SDK at once corrupt it, and a disk-wide search for it costs minutes.
- `BASE-13` holds for the leader too: no deleting untracked files without the user's yes, `git status` before and after an install / uninstall on a bind-mounted environment, `.env` edits only by named keys after a backup, and the message to the user lists the keys changed.

## Rule compliance
Every task carries its rules explicitly — procedure and formats in `references/rule-packs.md`:
- The task board's `Rules` column lists the packs per task (`BASE` and `COST` implied); a rule ID is pack + item number (`COMPACT-3`), plus the task's `AC-n` and `SEC-n`.
- **Brief**: every developer, reviewer and qc brief follows the **Brief skeleton** below, including the rule list — one line per rule ID with its check text and the must-read path per pack (§1). Agents open the reference files only for the rules the task exercises. Never brief with "follow the skill" alone.
- **DONE gate**: the notes hold a `## Rule compliance` table, one row per rule ID with evidence; spot-check self-attested rows. Missing rows → send back (not a fix round).
- **Verdict gate**: reviewer and qc verdicts carry a `## Rule check T{id}` table.
- **Coverage**: `done` when every observable rule ID has a verifier `pass`; rules nobody could observe are reported `unverified`.
- **Ledger**: verifier `fail`s go to `$TEAM_WS/rule-violations.md`; a rule that fails in two tasks becomes a warning line in every later brief.

## Brief skeleton
Every agent brief follows this order — fill each line, write `none` rather than dropping one:
1. `TEAM_BIN=… TEAM_STATE=… TEAM_WS=… TEAM_TOOLS=…` and `PLAYWRIGHT_DIR=…` when a browser is used.
2. `Task T{id} — <title>`; mode (implement / UI design / fix / quick pass / review / QC / sign-off); side `be` or `fe`; the model it was spawned on (Model per role).
3. **Skills to load** by name (`ai-dev-team:implementation`, `ai-dev-team:pwa-headless-ui`, `ai-dev-team:ui-ux-design`, `ui-ux-pro-max` when installed, …); the notes list the skills called.
4. The task's board row.
5. **Rule list**: one line per rule ID with its check text — the task's packs plus `BASE` and `COST` for a developer, only the rules the role verifies for a reviewer or qc (`references/rule-packs.md` §1).
6. **Scope**: the files; the reuse notes for the task (what the plan says to reuse, `$TEAM_STATE/capabilities.md`, `BASE-16`); integration-point lines the task must not edit (Phase 3 step 3); for UI work and design QA the profile's `ui_widths` (or `ui_sizes`) × `ui_themes`, the states to sweep, every renderer of a changed shared component (`SWEEP-4`), `ui_seed`, `ui_flows`, the approved mockup path in `mockup_dir`, the profile's `design_taste` and the spec's main tasks (`ai-dev-team:ui-ux-design` → `references/ease-of-use.md`).
7. **Inputs**: the spec / plan / UI-spec / threat-model sections, the notes of tasks it depends on, ledger warnings.
8. **Commands** from the profile (related tests, mapped guards, type-check, build — wrapped where heavy, light ones direct); for a reviewer, how to get the task diff (the task's commit, or `$TEAM_BIN/rule-checks.sh task-diff T{id} -- <task files>`).
9. **Report** format (`references/rule-packs.md` §6 developer, §7 verifier) and the `DONE` / `BLOCKED` / verdict line.

## Unattended runs
In the first question the leader asks anyway (Phase 2 or the plan gate, together with the Fable policy), it also asks whether the user stays at the machine (header `Presence`): `I stay` or `I will be away — ask everything now`. Write the answer in the board notes (`presence: away (user, <time>)`). The answer holds for that sitting only: when the user types in the session, `away` ends (write `presence: present (user typed, <time>)`), and a resume in a new session or after more than ~6 hours asks `Presence` again in the first question the leader asks anyway; the Fable policy is shown in the first board line of a resume so the user can change it. While the user is present, a task the leader would add on its own (a follow-up from a review note, parity with another app) is proposed to the user first, not started.

When the user will be away:
1. **Ask everything up front**, in as few AskUserQuestion calls as possible (4 questions each): open scope and acceptance points, every product decision (data deletion, lifecycle, public-API changes, writes to another repository, access trade-offs), the visible assumptions of any UI (themes, print colours, imagery, density), the Fable policy, whether to run the full suite, and whether to commit / push when done.
2. **Settle UI design before the user leaves**: run the design gate (`DESIGN`) through the user's pick while they are there; only build and verification run unattended.
3. **No questions during the run.** A new question gets the option marked Recommended, recorded in `$TEAM_WS/decisions.md` (question, choice, why, task) and the run goes on. Irreversible or outward actions — deleting data, writing to another repository, changing a public API, an access trade-off, a commit or push not approved up front — are never decided this way: only that task stops (`blocked: needs user`), independent tasks continue.
4. A design option that had to be picked while the user was away (rework after rejection, a new screen) is the one design QA rated best, listed in the report for review.
   A user gate of the plan (a review stop such as "the user checks the real UI before wiring the API") that the user waived up front ("do everything", "design QA approves in my place") is passed by the proxy they named and listed in the report; the leader does not stop at it. Decisions taken by default until then go in `decisions.md` and in the report, not into a question. A dependency, tool or package the approved plan already names needs no new question.
5. The Phase 6 report starts with "Decided while you were away": every `decisions.md` entry and every task held for the user.
6. **Watchdog**: background agents give no news until they finish, and a leader that ends its turn while only they run wakes up only when one reports. Whenever the leader ends a turn with agents running, it keeps one checkpoint armed (`Monitor` or `ScheduleWakeup`, about every 20 minutes). At each checkpoint it checks every running agent: no new output for ~20 minutes, a task notes file that stopped changing, or a test or build process older than its timeout means the agent is stuck — read its notes, stop the hung process, and brief a fresh agent from the notes (`Error handling`: agent unresponsive). This holds whether or not the user is present. An agent that ended its turn while its own background command runs is not stuck: it is resumed when the command finishes (`BASE-14`) — check the command with `run-heavy.sh --status` instead. The checkpoint prompt is plain text (`watchdog checkpoint: check running agents, post the board line`), never the `/ai-dev-team:dev-team` command — that would load this whole skill into the context again every 20 minutes. Keep one checkpoint armed: a new one replaces the old, and a checkpoint whose agents have all reported is skipped.

## Device preview (QR to the user's phone)
When the user asks to see the app on their phone ("tạo QR kết nối", "open it on my phone", "QR code"), or when a mobile UI task has just reached `done` while the user is present (offer it then, header `Device`: `Show on my phone (QR)` / `Skip` / `At the end`), the leader runs `node $TEAM_BIN/device-preview.mjs` on the current build — at once, between tasks, without stopping running agents. Phone and machine must share the Wi-Fi; nothing is installed on the phone except the app under test. **Show the QR in the reply**: the script prints it as plain block characters between `QR-BEGIN` and `QR-END`; paste that block inside a code block in the message to the user, with the URL under it, so the user scans it straight from the session (add `--light-bg` when the user's terminal has a light background). An image or a browser window is only a fallback.
- `web <dir>` — a built web app, PWA or Flutter web build, served on the LAN address with a QR to it; the phone opens it in its browser. No native plugins (camera via plugin, printers, push); service workers and camera APIs need HTTPS, which this mode does not provide.
- `url <dev server url>` — a QR for a dev server already listening on all interfaces (Vite `--host 0.0.0.0`, `flutter run -d web-server --web-hostname 0.0.0.0`); reloads show changes.
- `android-pair` — Android 11+: the user opens Developer options → Wireless debugging → *Pair device with QR code* and scans; the script pairs and connects adb, then the leader runs `flutter run -d <serial>` (hot reload on the real phone, native features included) or `npx cap run android --target <serial>` (Capacitor, with `--live-reload --host <LAN ip>` for reloads). Needs adb (Android platform-tools; found in the Android SDK when it is not on PATH). QR pairing relies on mDNS, which some networks block: after 90 s the script prints the fallback — ask the user for the IP:port and 6-digit code of *Pair device with pairing code* and the IP:port on the Wireless debugging screen, then run `android-code <pair ip:port> <code> <connect ip:port>` while that dialog is still open.
- **Which network**: the script prefers the Wi-Fi interface and lists every LAN address; a machine on cable and Wi-Fi has two. Ask which network the phone is on when unsure, and point the app's API or demo URL at the address on that network (a debug build's LAN host, the CMS's site URL) — the phone cannot reach an address on the other network.
- `apk <file>` — a QR to download a built debug APK; the user allows installs from the browser once.
- iOS needs a Mac with Xcode for a native build; on other machines the iPhone gets the `web` or `url` mode.
- Only the local network: the server binds to the LAN address, stops by itself after 30 minutes (`--minutes`), and the leader stops it when the user is done. Exposing the app on the internet (a tunnel) needs the user's explicit yes each time. The profile's `local.md` records `device_preview` (the modes this machine supports).

## Phase 0 — Context check
1. **Paths** — the team keeps its state in the repo folder `.ai-dev-team/` (committed with the work, `qa-artifacts/` ignored); resolve these once per session (`references/team-paths.md`) and put their absolute values in every brief: `TEAM_BIN` (plugin scripts), `TEAM_STATE` (`<repo>/.ai-dev-team`), `TEAM_WS` (`$TEAM_STATE/workspace`), `TEAM_TOOLS` (shared QA tools on this machine). Team files of older versions are moved there first (`team-paths.md` §4).
2. `$TEAM_STATE/project-profile.md` missing, older than ~30 days, or the stack changed → Phase 1; else skip it. Compare the profile with the current `ai-dev-team:project-profiling` template: every missing field (budget fields, `ui_seed`, `ui_flows`, `playwright_dir`, `mockup_dir`, …) is filled in by the step of that skill that defines it, before any brief. Commands that hold a versioned plugin path (`…/ai-dev-team/<version>/skills/project-profiling/references/…`) are rewritten to the literal `$TEAM_BIN/…`. Machine values (`playwright_dir`, `heavy_workers`, the app URL) are read from and written to the git-ignored `$TEAM_STATE/local.md`, never the committed profile; a field is written once, in front matter. A `mockup_dir` that git ignores is asked about once (`ai-dev-team:project-profiling` step 7). Missing `.env` keys reported by the resolve snippet (`env-drift`) are told to the user before any build or install uses that file.
3. `$TEAM_WS/`:
   - absent → fresh run.
   - present with unfinished tasks on the board (`in progress`, `review`, `fix`) and the user says continue/resume, or asks something that fits the same feature → **resume** (below).
   - present, all tasks `done`, and the request is new → move it to `$TEAM_STATE/workspace_<YYYYMMDD-HHMM>/` and start fresh. If unfinished tasks remain and the request is unrelated, ask the user before archiving them.
   - a follow-up on finished work ("only redo the design", "improve X") → rerun only the affected phase or task.
4. **Plugin updated during a run** (a `/reload-plugins`, or this skill loaded from a newer version than the `TEAM_BIN` in the board notes): resolve `TEAM_BIN` again from the newly loaded skill, write it in the board notes, `SendMessage` the new path to every running agent, and use it in every later brief; agents keep the skills they already loaded until their task ends. On a machine with several Claude Code configurations (accounts, `CLAUDE_CONFIG_DIR`), the plugin is updated in each one — an update in one leaves the others on the old version.
5. **Resume**: read the task board's Status and Rounds columns. For each unfinished task read `$TEAM_WS/04_dev_T{id}.md` and `git diff`, then brief a fresh developer with "continue T{id} from these notes" (or a fresh reviewer/qc for a pending verdict). Round counts come from the board, never restart at zero. A previous Phase 5 `runId` in `$TEAM_WS/run_meta.json` → resume it with `resumeFromRunId`.

## Phase 1 — Profile (leader)
Follow `ai-dev-team:project-profiling`: detect the stack, verify the commands, record conventions, UI presence and the budget. The profile goes to `$TEAM_STATE/project-profile.md` (`.ai-dev-team/`). Run long verification commands in the background through the wrapper and keep only trimmed output in context. A greenfield repo still gets the budget; its commands are profiled again right after the scaffold task. The profile step also writes the project's capability index `$TEAM_STATE/capabilities.md` (`ai-dev-team:project-profiling` step 5a) when it is missing; developers add to it as they build.

## Phase 2 — Spec (leader with the user)
0. **Research** (only when the user chose it — Routing, `references/request-research.md`): show the options summary and ask the user to pick the option and the optional items; the picks are the starting point of the spec, and nothing settled there is asked again below.
1. **With superpowers**: when `superpowers:brainstorming` already ran on this request earlier in the conversation (it may fire before `dev-team` is invoked), continue from its questions and the user's answers instead of starting over — never drop an answered or pending question. When brainstorming offers visuals (its visual companion), use them only for low-fidelity layout or flow sketches; visual mockups of a `has_ui` spec are always made by `developer` in UI design mode under `DESIGN` (Phase 3), never drawn by the leader. Otherwise run `superpowers:brainstorming` with the user's request (it explores context, asks one question at a time, gets approval and saves the spec — tell it to save to `$TEAM_WS/01_spec.md`, its mockups and visual-companion files to `$TEAM_WS/mockups/` (never `.superpowers/` in the repo), and not to commit, since the user commits the team's files with the work). **Without**: write the spec with `ai-dev-team:spec-writing` and ask open questions with AskUserQuestion (max 4 at a time, proposed defaults first).
2. Make sure the spec — wherever it was saved — has the header fields of `ai-dev-team:spec-writing`: `has_ui`, `security_sensitive`, acceptance criteria numbered `AC-1…`, open questions resolved. Copy or link it as `$TEAM_WS/01_spec.md`.
3. **Existing integrations first**: when the feature touches another system (auth server, CRM, another app or repo, synced data), read how the existing sibling apps and the synced data already do it before proposing a flow, and propose the same pattern unless the user wants otherwise. Any write to another repository needs the user's yes first, naming the repo and files; the plan lists those tasks separately.
4. Product decisions stay with the user: entity lifecycle (`ai-dev-team:technical-design` → `references/record-lifecycle.md`), public-API changes, data deletion, AI-crawler policy — ask with a proposed default.
   **Access trade-offs too**: anything that lets data stay reachable after access is removed (cache lifetime of signed or public URLs after revoke, trash or deactivate; tokens or sessions valid after logout; stale permissions) or weakens privacy is never accepted by the leader or a reviewer. Present it to the user with the exposure window and the alternatives, and record the answer in the spec. This holds when it first shows up as a reviewer finding during the build.
5. **Mobile platform choice.** When the request needs an iOS/Android app and the profile has `mobile_platform: none`, ask with one AskUserQuestion (header `Mobile`): `Flutter (Recommended)` — one Dart codebase, native performance; `Capacitor (wrap the PWA)` — fastest, WebView limits; `Native apps` — Swift/SwiftUI + Kotlin/Compose, two codebases, highest cost. Same when a developer returns `needs-user-decision: mobile platform`. Details: `ai-dev-team:pwa-headless-ui` → `references/mobile-options.md`.

## Phase 3 — Plan (leader + agents in parallel)
1. Spawn in one message, when the spec calls for them:
   - `has_ui` → `developer` in **UI design** mode → `$TEAM_WS/02_ui-spec.md` and the mockup HTML, pack `DESIGN` (`ai-dev-team:ui-ux-design` → `references/design-gate.md`). For a new product, template or app, confirm the screen inventory with the user before the mockups are drawn. Mockups come in two stages (`design-gate.md` §3): stage 1 — three representative pages per option; design QA by a fresh `reviewer` on `sonnet`, open the passing HTML for the user (`xdg-open` / `open`, with its path), ask which option to build; stage 2 — the chosen option with every inventory page and preset, design QA again. No build task of that UI starts before stage 2 passes. When the project has a runnable frontend, stage 2 is built in that frontend with a fake data adapter (`design-gate.md` §3): it is the UI itself, so the plan's client tasks become wiring tasks; when the API does not exist yet, its contract is drafted from the approved adapter interface, reviewed for the server-side rules and confirmed before the server tasks start.
   - `security_sensitive` → `reviewer` in **threat model** mode → `$TEAM_WS/02_threat-model.md` with `SEC-n`.
2. Meanwhile write the plan: **with superpowers** `superpowers:writing-plans`, saved to `$TEAM_WS/02_plan.md`, no commit (stop when it offers an execution mode — the build loop below executes the plan; do not hand over to `subagent-driven-development` or `executing-plans`); **without**, `ai-dev-team:technical-design`. Either way the plan meets `technical-design`: contracts between modules, decisions with reasons, default stack and latest-stable toolchain for greenfield, 3–8 tasks sized for throughput.
3. **Reuse and integration points**, written into the plan before the board: for each task, what it reuses from the project (`$TEAM_STATE/capabilities.md`, a search by name when the index has nothing) or why it needs something new (`BASE-16`). Then the **integration points** several tasks would each edit by one line — the app entry that registers overrides or providers, the router, a DI module, a barrel export, a manifest or plist, the nav menu: either one small setup task (on `sonnet`) adds every task's hook first (an empty `<feature>Overrides()` called from the entry, a route stub), or the leader adds those one-line registrations itself after each task is done. Each task then owns only its own files, and tasks that differ only in that one line run in parallel instead of one after another.
4. When the UI spec and threat model are back, write `$TEAM_WS/02_tasks.md` in the task-board format of `ai-dev-team:technical-design` (ID, title, owner `be`/`fe`, depends, files, tags `ui`/`pwa`/`mobile`/`security`, `Rules` per `references/rule-packs.md` §5 incl. `AC-n`/`SEC-n`, verify command, Status, Rounds). Contradictions between spec, UI spec and threat model go to the user.

**User gate:** show a short plan summary (task count, key decisions, risks), and, when no earlier question set it, the Fable policy in the same AskUserQuestion (Phase 4, Model per role). Wait for approval when: greenfield, data migration, public API change, or > 8 tasks. Otherwise proceed and say the user can stop you.
A reply that changes scope is not approval: update the spec and board, show the user only what changed, and wait again whenever the gate applies. A scope change while tasks are running: tell the affected agents to stop at a safe point, update the spec, confirm the new scope with the user, then send the revision — one revision per confirmed change, not one per message.

## Phase 4 — Build loop
Topology is **hub-and-spoke**: agents talk only to the leader. Handover lives in files (task notes, the board, the rulings ledger), never only in an agent's memory. Each agent's first message lists its tools — one missing a tool it needs is restarted or that step is done by the leader.

For each task in dependency order (update Status and Rounds on the board as you go):
1. **Build** → a fresh `developer`, told the task's side (`Owner`): "Implement T{id}" + task row, rule list, the relevant spec / plan / UI-spec / threat-model sections, notes of tasks it depends on, ledger warnings. Wait for `DONE` / `BLOCKED`, apply the DONE gate.
   **Task diff**: reviewers must be able to read exactly this task's change. When the user approved commits, commit each task on its own when it reaches `done` (one commit per task, never several tasks in one). Otherwise run `$TEAM_BIN/rule-checks.sh task-base T{id}` right before the developer starts; the reviewer gets `rule-checks.sh task-diff T{id} -- <task files>` in its brief.
   Every new task gets a new developer, even when an earlier developer "knows the code": hand over through that task's notes. Only fix rounds of the same task go back to the same developer. The same holds for verifiers: every task gets its own reviewer and qc; a new task's review or QC is never sent to an agent that verified another task.
   A task tagged `security`, or one that implements authentication, authorization or data access, starts only after the threat model is back and its `SEC-n` are on the board row; other tasks may start meanwhile.
   **Fill the slots**: whenever a task starts or reaches `done`, walk the board and start every task that is ready — dependencies `done`, files disjoint from the running tasks, no shared built output, no shared test data or environment in use (a task that seeds, resets, migrates or deletes data on the demo / test database or site never runs while a qc or browser check is using that environment) — until `max_agents` developers are running; reviewers and qc start as soon as their task is ready, within `max_verifiers`. A ready task left waiting gets the reason in the board notes. When the leader decides a dependency on the board does not hold (a task can start without the one it lists), it edits that row's `Depends on` and writes why in the board notes before starting the task — the board is what a resume reads. Serial work by habit wastes the budget the profile allows.
   Tasks run concurrently, one developer each within `max_agents`, only when **isolated**: no dependency, no overlap in their files (shared components, styles, language files, tests, build config included), no shared built output, and no shared data or environment that one of them changes while the other checks it. Before starting two tasks together, compare their `files` cells on the board and write `parallel: T2 ∥ T3 — files disjoint` in the board notes; any shared path, or a task still in review or fix on files the new one touches, means they run one after the other. Two tasks of one app (frontend or backend) that touch the same module, entity or test directory are not isolated — run them in sequence, or each in its own git worktree (`isolation: "worktree"`, merged back by the leader).
2. **Verify in parallel** — one message: a fresh `reviewer` (model per **Model per role** below; "Review T{id}": code + security + design QA as the task's tags and packs require) and a fresh `qc` ("QC T{id}"; skipped on light-tier routes unless a criterion needs runtime proof). Brief each with the task row, the sections it needs, the task notes, and the packs it verifies with their must-read files. Reviewers do not run suites; qc does not rerun the developer's tests.
3. **Fix**: only blocker/major/critical/high findings, `QC_FAIL` defects and rule-check `fail`s open a fix round. Wait for both the reviewer and qc verdicts, then merge everything into **one** fix request to the same developer (`SendMessage`; a fresh one with the notes if it is gone) — round 1 carries every such issue from both verifiers, so later rounds are only for what the re-checks still find. Minor/low findings ride along in a round that is opening anyway. When none opens and they are still to be fixed (the project's own rules may require fixing every finding), they get one **quick pass**: the same developer if it is still alive, or a fresh one on `sonnet` with only those findings and the files; no sweep beyond the states the fix touches, related tests only, re-checked by the reviewer on the diff alone, no qc. A quick pass is not counted as a round. Otherwise they go to the Phase 6 report. Re-verification goes only to the agents that raised issues, via `SendMessage`. Increment Rounds; **max 3**. Still failing after round 3 → **escalation**: one fresh `developer` — on `fable` when the run's Fable policy allows it (`auto`, or `ask` and the user said yes), otherwise on the proposed model — briefed from the notes and all rounds' findings, to find the root cause and fix it; its review and QC follow as usual. Still failing → mark `blocked` and tell the user.
   Before opening a round on a finding about another task's files, or one from a run that started before that task's last round, check it against the current tree (one file run or a `git diff` look); a finding the tree no longer shows is closed, not sent. A finding the reviewer calls an "accepted trade-off" that falls under the Phase 2 access trade-offs goes to the user, not into the spec as accepted.
   `QC_BLOCKED` (environment, missing service, browser needs the user): fix the environment or ask the user; the task is never `done` while qc is blocked.
4. **Done** when coverage holds; record `unverified` rule IDs on the board and this task's `fail`s in the ledger. Retire the task's agents.

**Model per role** — every spawn passes `model` explicitly, chosen from this table, and the brief names it (Brief skeleton line 2); the agent file's default (opus for developer and reviewer) is only a fallback, and a spawn that leaves it out runs low-risk reviews and scaffolding on opus by accident. High-risk task: tagged `security`; or a server-side (`be`) task that carries `ABUSE`, `LIFE`, `QUERY` or `SEC-n`, or touches auth, permissions, payments, data deletion, schema or migrations, concurrency (locks, races, queues) or money/quantity calculations. A client (`fe`) task that only shows data and calls the server's API is not high-risk for carrying `LIFE`, `LIST` or `QUERY` (its checks there are UI behavior; the server enforces the rule) — unless it stores credentials or tokens, decides where a credential or token is sent (headers, image or file hosts, redirects), decides access on the device, computes money or quantities, or keeps data offline that the server would refuse; a client task carrying a `SEC-n` about tokens or credentials is high-risk.

| Work | Model |
|---|---|
| developer — normal task, UI design mode | opus (default) |
| developer — small low-risk task: about 3 files or fewer, one module, not high-risk, no new contract (a follow-up tweak, a toast, a default value, a script fix) | `sonnet`; after two failed fix rounds the next round goes to `opus` |
| developer — design stage 2 composing from a frozen kit (one per screen group, run in parallel), light-tier task (small change, layout complaint), template / theme pack, site template or theme for a CMS or app (layout, styles, tokens — no business logic, data or security code) | `sonnet` |
| developer and reviewer — removal or clean-up task (deleting code, files, configs or dead paths with no new logic), unless what it removes guards access, security or data | `sonnet` |
| developer and reviewer — content or data task: sample data, demo seed content, translations and language strings, fixtures, images, copy — no schema, logic, access or money code | `sonnet` |
| developer — `env` task (a failing install, seed, build setup or service start) | `sonnet` |
| developer or reviewer — Fable cases below, per the run's Fable policy | `fable` |
| reviewer — high-risk task, threat model, full audit, Phase 5 dimensions and verifiers | opus (default) |
| reviewer — any other task review | `sonnet`; an `uncertain` on a correctness question → one opus re-check of that question only |
| qc — per task and sign-off | sonnet (default) |

Haiku is not used: every role judges code, screenshots or rules.

**Project agents**: when the project ships its own implementer agents for an area (`.claude/agents/`, e.g. a backend agent that knows its framework rules), the leader may build that area's tasks with them instead of `developer`, on the model their file sets unless this table needs higher. The same Brief skeleton, rule list, notes file, `## Rule compliance` table, reviews, qc and gates apply; the brief names the plugin's report format, since the project agent does not know it.

**Fable only by the user's policy** — it costs twice Opus and its turns are slower, so the leader never chooses it on its own. The cases where it fits:
1. A task still fails after 3 fix rounds (escalation, step 3).
2. A bug that is hard to reproduce: intermittent, a race, or only on a real environment.
3. A task that is high-risk **and** complex: spans several modules, involves concurrency or money, or migrates a lot of data.
4. A full security audit; the plan of a greenfield project or of a feature with 8 or more tasks.

**Fable policy, set once per run while the user is present.** AskUserQuestion blocks the session until the user answers, so the leader never waits on a Fable question mid-build. Instead it asks for a policy once, in the first AskUserQuestion it makes anyway (Phase 2 questions or the plan gate), header `Model`, listing the tasks that already meet case 3 or 4 and the cost:
- `Use Fable automatically, report it` — every case above runs on Fable without asking; each use is reported.
- `Ask each time` — the leader asks when a case arises; that task waits for the answer (a user away from the machine holds it up).
- `Never use Fable` — the proposed model runs in every case.

Write the answer in the board notes (`fable-policy: auto | ask | never (user, <time>)`); a resume keeps it, and it lasts until this run's workspace is archived. Routes that ask the user nothing (light tier) use `ask`. The policy covers only the four cases — every other spawn keeps its model from the table. The user can change it at any time ("stop using Fable", "use Fable from now on"): update the note, applied from the next spawn; agents already running finish on their model. Under `ask`, the options per case are `Use Fable` and `Keep <proposed model>`. The Phase 6 report lists every agent that ran on Fable: task, role, case and why.

**Progress to the user** (in their language, short): when a task starts or reaches `done`, one board line — `done 6/9 · running M2, T3 · waiting: sign-off · next: Phase 5`; when about 5 minutes have passed without news, one line on what it is doing, what comes next and a rough time left from similar measured tasks. Waiting tasks are named with their reason (dependency, queue, user decision), so the user never has to ask what is left. Every progress message, and every answer to "where are we", opens with that board line (done · running · waiting with reasons) before any detail of the latest task. A background agent gives the leader no news until it finishes, so when one is expected to run long (UI design, a normal build task) the leader sets a checkpoint about every 5 minutes (`ScheduleWakeup` or a `Monitor` on the agent's output) and at each one reads the agent's progress and posts the line; it stops the checkpoints when the agent returns.

Replace any agent early when its context passes ~500k tokens: ask it to write its notes first, then brief the replacement from them.

**Test cost** (put in every developer brief): per task only the related tests of the changed files + mapped guards, type-check, build once at the end; per fix round only that round's files; a failure in a test the task did not touch → rerun that file once, then report it `not mine`. The full suite runs once at sign-off, or earlier only when a change touches shared infrastructure. When the profile records `tests: none`, say so in the brief: evidence is the reproduction steps and command output the task criteria need; the plan should contain a task that adds a test runner when the user agrees.

After the last task is confirmed: **one** `qc` in sign-off mode — full, or light when the run had only light-tier tasks (`references/resource-budget.md` §5). Phase 5 starts only after sign-off passed — never in parallel with it, since sign-off can still send work back.

## Phase 5 — Final review (Workflow)
On feature, greenfield and mobile routes it runs only when the board has **4 or more tasks**, any task is tagged `security`, or the spec is `security_sensitive` — per-task reviews cannot see how many tasks interact, but with 1–3 ordinary tasks the per-task reviews cover it. Skipped → say so in the Phase 6 report. The review-only route always runs it. Build `args.dimensions`: always `correctness`; `security` if `security_sensitive` or any `security` task; `ui` if `has_ui`. Pass `args.scope` (file list or `git diff` range), `args.mode` (`'feature'`, or `'review-only'` on the review-only route), `args.specPath` / `args.designPath` when they exist, `args.agentPrefix` (`'ai-dev-team:'` by default) and `args.maxAgents` (the profile's `max_verifiers`). Read `references/final-review.workflow.js` from this skill's directory and call Workflow with its text as `script` — a `scriptPath` into the plugin's install directory is rejected, since that directory is outside the project. Use `scriptPath` only for a path the Workflow tool itself returned (to iterate on or resume that run). Every dimension and verifier is a `reviewer` agent; in feature mode the reviewers focus on cross-task interactions, since per-task review already covered each task. The result is `{ confirmed, uncertain, minor, missingDimensions }`.

Write the `runId` to `$TEAM_WS/run_meta.json`; wait for the completion notification, never predict results. `confirmed` → back to Phase 4 as a fix round, then resume only the affected dimension. Re-verification after these fixes is qc's (one `qc`, not the leader): the related tests of the fixed files and a sweep of the states they touch; the full suite again only when the fixes touched shared code (shared modules, schema, build config). The leader never runs suites or builds itself. `uncertain` → list for the user. Save the result to `$TEAM_WS/06_final_review.json`.

## Phase 6 — Report (to the user, in their language)
Decisions taken while the user was away (unattended runs) first, then what was built, files changed, test/QC results with real numbers, review outcome (confirmed fixed / uncertain / minor), rule compliance (`unverified` IDs, rules that failed in two or more tasks), anything skipped or blocked and why. No commits unless the user asks; messages English, imperative, no AI attribution.

## Data passing
- Files in `$TEAM_WS/`: `01_spec.md`, `02_plan.md` (or a link to the superpowers plan), `02_ui-spec.md`, `02_threat-model.md`, `02_tasks.md`, `04_dev_T{id}.md`, `05_qc_report.md`, `qa-artifacts/`, `rule-violations.md`, `06_final_review.json`. Final deliverables are the code in the repo.
- Messages carry verdicts and short summaries; details live in files.

## Error handling
| Situation | Action |
|---|---|
| Agent fails once | Retry once with the same input. Fails again → continue without it and record the gap in the report. |
| Usage limit, auth expired, permission denied | Do not retry. Write `$TEAM_WS/gaps.md`, keep the board's Status/Rounds current, report to the user (with the reset time if known); the next "continue" resumes from Phase 0. |
| Agent unresponsive | `SendMessage` a status ping and re-send the instruction. Still stuck → a fresh agent of the same type briefed from the notes. |
| Agent ended its turn waiting on its own background command | Normal (`BASE-14`): it is resumed when the command finishes. Check the command (`run-heavy.sh --status`, the process age); only a command past `AI_DEV_TEAM_TIMEOUT` or an agent silent after its command ended is a problem — next row. |
| Agent finished without a report, or waiting on a hung command | Found by the watchdog (Unattended runs 6): stop the hung process (a test runner or build older than `AI_DEV_TEAM_TIMEOUT`), then resume the agent or brief a fresh one from its notes; record the hang in the notes so the next agent splits or fixes that step. |
| `QC_BLOCKED` | Fix the environment if the leader can (start a service the profile names), else ask the user; never mark the task `done`. |
| Repo has no tests / lint / type-check | Profile records `tests: none` etc.; rules that need them are `n-a` with that reason; offer the user a task that adds them. |
| Workflow agent returned null | Report missing dimensions; resume with `resumeFromRunId`. |
| Conflicting findings | Keep both with sources; ask the user only if it changes behavior. |
| 3 fix rounds exhausted | One escalation developer — on `fable` per the run's Fable policy (Phase 4 step 3). Still failing → mark `blocked`, stop dependent tasks, report with the root-cause analysis. |
