# Design gate: from request to an approved mockup

A mockup is the user's first look at the work: it is checked against the design skills, the whole product scope and the plugin's layout rules before the user sees it. This file is the procedure for UI design mode and the `DESIGN` rule pack.

## Contents

## 1. Inventory first
Before drawing anything, list what the product type needs — from the request, the domain and the platform's conventions, not from the screen that triggered the request:
- **Product type** in one line (site template for a CMS, ordering app, admin console, marketing page, …).
- **Screens / page types** it serves. A site template for a CMS: home or featured page, article, category blog and list, search results, the component pages it hosts, login and profile, 404 / error, offline / maintenance, print view if the CMS has one. An app: every tab, list, detail, form, empty and error state.
- **Chrome and regions**: header (logo, primary navigation, search, account), secondary navigation, breadcrumbs, sidebars or module positions in use, footer, notices, cookie / consent, skip links.
- **Real content per screen**: names, lengths and amounts from the domain (`REAL`), worst cases included, taken from the product's real data where it exists (a read-only count and sample per object type from the local database or API: kinds of media, aspect ratios, name lengths, which optional fields are filled; private values masked) so the mockup shows what users really see, items with and without optional content included (`REAL-9`) — one content set for the whole product, reused by every mockup and by the seed data.
- **Main tasks**: the 3–5 things users do most, with the step count each option needs (`EASE`, `references/ease-of-use.md` §1); the profile's `design_taste` applies to every option.
- **Visual references**: two or three apps or sites the user likes for this product, the style they want (minimal, POS-like, editorial, playful, …) and what they do not want. When the user has none, ask whether to research comparable products first (header `References`: `Find similar apps (≈5–10 min)` / `Show mood directions now`); for a redesign, or after a rejected round, the reference gallery of §1a is not optional.
  - **Research** (when the user says yes): the designer finds 4–6 comparable products with WebSearch (product sites, App Store / Google Play listings, public docs with screenshots), captures their public pages with Playwright headless through `run-heavy.sh` into `$TEAM_WS/mockups/references/` (images stay out of git), and notes per product what is worth learning — navigation, density, data presentation, palette, component style. Learn patterns only: never copy another product's logo, name, imagery or exact screens (`REAL`). Skip sites that refuse automated access.
  - **Mood directions**: 4–6 short directions (a name, palette swatch, type pair, one sample component each), each citing the references it draws on when research ran; the user picks one before any option is drawn.
- **Visible assumptions**: every choice the user will see that the request did not settle — print colours (light or dark paper), default theme, use of photos, density, tone of copy, which items show — listed as a choice with a proposed default and the domain's common practice, never decided silently.

- **Redesign: keep and drop first**: when the request redoes an existing design ("make it new", "the current look is rejected"), ask the user what may carry over — palette, fonts, component kit, layout frame, logo, imagery — with "nothing" as the default. The designer's brief lists what may be kept and a ban list of everything else; an option that reuses the banned palette, fonts, kit or frame fails (`DESIGN-12`). Drafts made from the current code or kit anchor every option to the look the user rejected.
- **After a rejected round** (`DESIGN-13`): the next round never starts with full options. First the user's references, or the reference gallery when they have none (§1a), then overview boards to pick from. After two rejected rounds the stop rule applies (§1a, `DESIGN-21`): a fresh designer, and nothing drawn until the rejection review, the calibration matrix and the references are done.

When the request is a new product, template or app (not a change to one screen), the leader shows this inventory and the visible assumptions to the user and gets a yes before the mockups are drawn; for a smaller design task, the visible assumptions alone are asked. A missing page type found after the mockups costs a full redesign.

## 1a. Choosing a direction before HTML
The direction is settled with cheap artefacts the user reacts to; HTML is drawn only for a direction the user approved.
- **Reference gallery** (`DESIGN-18`): 8–12 or more screenshots of real sites or apps — in the domain and outside it, chosen for ideas, not for the usual pattern — captured with Playwright through `run-heavy.sh` (or taken from a design gallery page when sites refuse automated access) into `$TEAM_WS/mockups/references/`, shown as one local HTML page with a one-line note per image (what is worth taking). The designer studies it and writes why the strongest pages look professional (section rhythm, type scale, grid, imagery treatment, detail finish); the user is not asked to pick or mark references unless they offer to; research lens agents may build it in parallel (`ai-dev-team:dev-team` → `references/request-research.md`).
- **When the user sends references**, ask how to use them before drawing (header `References`): `Mood only` (spacing, finish, colour level — layout new), `Follow one closely` (which one), `Take listed elements`. Then break each reference into an element checklist — navigation, hero, card or list row, buttons, cart or summary, type, colour, imagery — and let the user tick what comes from which reference. A design never splices whole screens of two references together.
- **Overview boards** (`DESIGN-17`): three directions as static images, one per direction, built in parallel by three `sonnet` designers, about 8 minutes each. Fixed scope per board: palette with roles and hex, type specimen with real text in the product's language, one phone frame of the home top, one item card, the primary button — nothing more; finish is raised within that scope, never by adding screens. The three directions spread along the axis the user's feedback has not settled (venue site ↔ ordering app, restrained ↔ vivid, classic ↔ new) instead of sitting at one extreme. The user picks one, or rejects all with the reason.
- **Calibration matrix** (`DESIGN-19`): when feedback words are vague ("modern", "old", "not like that") or the last two rounds swung between extremes, one image of nine small home-top variants on a 3×3 grid of the two unsettled axes, labelled A1–C3; the user answers with a cell (or "between B2 and C2"), and the next board or mockup is drawn at that position.
- **Stop rule after two rejections** (`DESIGN-21`): no new drawing. First a rejection review — crops of the rejected parts, asking which part is wrong (colour, type, layout, imagery, density, components, interaction) — then the calibration matrix, then the reference gallery. Drawing resumes only with a position on the matrix and the designer's written study of the references.
- **Market study after three rejections** (`DESIGN-24`): when one product has been rejected three times in a run, the leader stops proposing directions of its own. A fresh designer studies 8–12 market-grade examples of the product type (best-selling templates, award-winning sites, leading apps), writes what makes them professional, and synthesizes one original design from that study and the project's identity. The user approves or rejects the result; they are not asked to choose among references or templates.
- **Divergence check** (`DESIGN-22`): every board or option records its value on fixed axes — shape language (corner radius, borders, elevation), layout skeleton of the phone and desktop home, navigation model, type pairing, palette, imagery treatment, position of the primary action. Options of one round differ on at least three axes, two of them shape language and layout skeleton. A redesign also records the same axes for the current or last rejected design and for each reference: an option that keeps the rejected skeleton, or matches one reference on three or more signature elements without the user asking to follow it, fails. The brief of a redesign carries a `Do not reuse (structure)` list (header, home top, list layout, panels) next to the ban list.

## 2. Design with the skills
- **Platform conventions for native apps** (Flutter, Swift / SwiftUI, Kotlin / Compose): the mockup follows the platform's design system — Material 3 on Android, Cupertino / Human Interface on iOS, or an adaptive mix the user chose — with its components (app bar, navigation bar or rail, sheets, FAB, segmented controls, native dialogs), its density and touch sizes, and adaptive layouts per `ui_sizes`: phone with bottom navigation, tablet with a navigation rail and list-detail or split panes. A layout that reads as a web page (centred column, web header and footer, hover-only affordances) fails.
- **Colour**: a palette for the product's domain (from `ui-ux-pro-max` when available) with a primary, an accent, semantic colours and neutral scales, contrast checked in light and dark; a palette of greys plus one colour fails.
- Load `ai-dev-team:ui-ux-design` (this skill) first; follow its Procedure and Visual identity steps, and read this file and `references/authentic-design.md` before drawing — the notes name both (`DESIGN-2`).
- When `ui-ux-pro-max` is in the session's skill list, run it for style direction, palette, typography pairing and layout patterns of the product type, then filter the result through Visual identity. Never install it.
- Apply the packs the screens need: `REAL` and `EASE` always; `COMPACT` for every phone-sized screen; `LIST`, `PTR`, `FEEL`, `CONN` when the inventory has those screens.
- The notes list every skill called (name and what it was used for).

## 3. Building the options: kit, files, two stages
A mockup file is generated token by token, so its size is its wait. Draw the choice small and the chosen option complete.
- **Stage 1 is HTML** (`DESIGN-14`): the stage-1 mockup of the approved direction is an HTML kit in `$TEAM_WS/mockups/` — never framework code, a framework build or code in the app's source tree, and never split across sub-agents (overview boards, built as HTML and rendered to PNG, are the leader's parallel spawns, not a designer's sub-agents). Framework code starts in stage 2, after the pick.
- **Stage 1 — the approved direction**: after the user picked a board (§1a), one HTML kit of that direction showing **three representative pages** of the inventory (e.g. home, one content page, the main component page) at phone and desktop width, one preset in light and dark, plus a `compare.html` that sets each reference beside the matching mockup screen (`DESIGN-20`). Several HTML options are drawn only when the user asks for them.
- **Asked for every screen at once**: when the user wants all screens mocked before choosing, the leader first gives a time estimate (from the screen count × options × themes × sizes) and offers stage 1 with three screens per option followed by every screen for the chosen option; the user decides.
- **Scope fixed before drawing**: screens, width tiers / `ui_sizes`, themes and presets are fixed in the brief before the designer starts; adding a size, theme or screen while it draws is a scope change (confirm with the user, then one revision).
- **Self-check before handing over**: the designer runs the §6 checks and the design-QA points (§4) on each option itself, fixes what fails, and records the result per option in its notes; the reviewer then confirms instead of discovering. Overview boards and the calibration matrix get the same self-check for `COMPACT` (paired buttons share a row on phones) and `REAL`. Small bold text never uses negative `letter-spacing` (Vietnamese and other diacritic scripts run words together).
- **Images and fonts** (`DESIGN-23`): photos come from the project's sample data or from the user; when they are not enough, from licensed sources in this order — official APIs with a key the user put in `$TEAM_STATE/local.md` (Unsplash, Pexels, Pixabay), Openverse and Wikimedia Commons, then free photo sites that allow direct download (Burst, Foodiesfeed) fetched without a faked `User-Agent` — with author and licence in `CREDITS.md` beside the mockup. A source that blocks automated access (a bot wall, 401/403) is not worked around with a browser or headers: switch to the next source at once and tell the leader in one line; ask the user only when no source fits. Fonts load through a Google Fonts `<link>` or an `@fontsource/*` package in `$TEAM_TOOLS`. No scraping of unofficial endpoints and no faked `User-Agent`. All photos of one screen share light, angle and colour grade. Images that ship in the product need the user's yes.
- **Stage 2 — build the chosen option in the project's own frontend**: when the project has a runnable frontend (profile dev / build commands; a new project runs its scaffold task first), stage 2 is real code in the project's framework and conventions — screens and components in the source tree, on the feature branch — with every page of the inventory, every state that matters and every preset the request names. Data comes through a **fake adapter**: an interface per data need (repository, service or store, in the project's pattern) with an in-memory implementation that serves the DESIGN-9 content set. The user and design QA look at the running app (web: the dev URL; Flutter: Flutter web or golden screenshots). After approval, build tasks only swap the fake adapter for the real API client and add loading, error and permission handling — the screens are not rewritten. Stage 2 code is reviewed like any code (reviewer + design QA). A project with no runnable frontend keeps stage 2 as the HTML kit below.
- **Fakes of existing endpoints come from real answers**: where the server already exists, the fake adapter returns responses captured from the running app (`curl` against the demo into fixture files beside the fakes), and a contract test checks the client's models against those fixtures. A hand-written fake shape is a guess — number formats, nullability and nesting drift from the server and only show up when the real API is wired.
- **Contract from the mockup**: when the API the screens need does not exist yet, the fake adapter's interface is the draft API contract. After the user approves stage 2, the leader turns it into the plan's contract, a reviewer checks it against the server-side rules the screens cannot show (pagination and limits, `LIFE`, `QUERY`, `ABUSE`, `SEC-n`), the user hears about any change it forces on the screens, and then the server tasks build it. When the API already exists, the fake adapter implements the existing contract and the screens adapt to it.
- **Kit first, screens as data**: the kit's base styles carry the themed scrollbars and smooth scrolling of `REAL-10` and the spacing scale `REAL-11` measures against. The designer first builds a small component kit for the option — tokens plus the 10–15 components the inventory needs (header, navigation, card, list row, form field, button, sheet, empty and error states) — then composes every screen from the kit as data. No screen re-declares markup or styles the kit already has. Most of the drawing time is output tokens, so this is the main speed lever.
- **Small files, edits not rewrites**: a mockup is a folder `$TEAM_WS/mockups/<name>/` — `index.html` (shell with switchers for option, screen, size, theme and preset), `kit.css` / `kit.js` (the kit), one `screens/<screen>.js` per screen (content as data). Revisions use Edit on the kit file or the screen file concerned; never rewrite the whole mockup. Drafts stay out of the rest of the repo (`.superpowers/` included). The approved option is copied to `mockup_dir` as its folder.
- **Stage 2 in parallel**: once the user has picked and the kit is frozen — the kit task is `done`, its review passed and no fix round is open on it — the leader splits the remaining screens into 2–3 groups (sign-in, lists, detail, settings, …) and spawns one developer per group within `max_agents`, groups owning disjoint screen files with the shared kit / components owned by one of them. An HTML-kit stage 2 runs on `model: "sonnet"`; a stage 2 in the project's frontend is production code and runs on the model the table gives a client task. A kit change during stage 2 goes through the leader to every designer. One design QA covers all groups together.
- **Light sweep in stage 1**: contact sheets at one phone size and the widest size, light and dark; every size, theme and preset only in stage 2.
- Each option already satisfies every check in §6; options never trade a rule away.
- Next to the mockup: one contact sheet per option from `overflow-check.mjs --sheet --touch 44` (`--touch 48` for an Android-sized app; stage 1: one phone size and the widest, light and dark; stage 2: every size, theme and preset). The self-check (`DESIGN-10`) includes that run: undersized touch targets are found by the script before design QA, not by the reviewer.

## 4. Design QA before the user sees it
- The leader sends the HTML and sheets to a fresh `reviewer` (`model: "sonnet"`) in design QA mode: inventory complete (§1), domain conventions and real content (`REAL`), main tasks walked as a new user with their step counts (`EASE`), no wasted space or overflow (`COMPACT`), contrast, states. Verdict per option: `pass` or the failing check IDs with the cell.
- Design QA also checks the user's visual references, platform conventions for native apps and the palette (`DESIGN-11`).
- Design QA covers every width tier (`ui_widths`, or `ui_sizes` for Flutter / native) and every theme in the profile's `ui_themes`; an option missing a theme or tier fails.
- Design QA runs `overflow-check.mjs --touch 44 --empty 24 --scrollbars --widths … --themes …` itself through `run-heavy.sh` and attaches the summary line; overflow and touch-target results are never taken from the designer's notes. It also runs the divergence check (`DESIGN-22`) and checks the order of buttons in every action group: primary on one side, secondary and destructive apart, the same order on every screen — a mixed order is `major`.
- **Evidence, not notes** (`DESIGN-16`): for every main screen the reviewer opens at least one full-size image per width tier × theme (cell images when the contact sheet is too small to read) and lists the files it opened in the verdict; a pass that rests on the designer's notes for any tier or theme is not a pass. Touch targets below the platform minimum (44 pt iOS, 48 dp Android, 44 px web) fail the option.
- A failing option is fixed by the designer or dropped before the user sees anything. At least one option must pass; otherwise the designer reworks and QA runs again (this is not a fix round of a build task).

## 5. Showing and asking
- **Only after design QA passed this round** (`DESIGN-25`): the board notes hold `DV{id} design QA PASS <time>` for the round being shown. A user asking for progress meanwhile gets the status, not the file.
- Open the HTML for the user (`xdg-open` on Linux, `open` on macOS, or a local static server with the URL) and give its absolute path. The leader looking at screenshots is not the user seeing the mockup.
- Then ask (AskUserQuestion when nothing else can run): approve the direction or change named parts; the user can also ask for changes. Build tasks start only after the user approves. Show `compare.html` with the mockup when references were used.
- **Build from a passed round**: build tasks start from the mockup round whose design QA passed; while a fix round of the mockup is open, tasks that build its screens wait for it.
- **Keep the approved mockup**: when the user picks, copy that option (the HTML reduced to it, plus its contact sheets) to the profile's `mockup_dir` in the repo, named after the feature (photos recompressed to about 150 KB each or pointed at the project's sample images), and write that path into the UI spec and the build tasks' notes so later changes compare against it. `mockup_dir: none` → nothing goes into the repo. Drafts and rejected options stay in `$TEAM_WS/mockups/`.

## 6. `DESIGN` checks
1. **Inventory** — the product type, every page type and chrome region it needs, real content per screen and the visible assumptions were listed before drawing; the user confirmed the assumptions (and, for a new product, template or app, the whole list).
2. **Skills used** — `ai-dev-team:ui-ux-design` was loaded, and `ui-ux-pro-max` was run when it was available; the notes name them.
3. **Kit, files, two stages** — stage 1 options live in `$TEAM_WS/mockups/<name>/` as a component kit plus one data file per screen, revised by edits; stage 2 is built in the project's frontend with a fake data adapter when the project has one, otherwise as the HTML kit; stage 1 shows three representative pages per option at phone and desktop width, light and dark; stage 2 shows every inventory page and requested preset for the chosen option only; no draft was written into the repo.
4. **Rules hold in every option** — every option passes `REAL` and `EASE` and, for phone-sized screens, `COMPACT`; contact sheets sit beside the HTML.
5. **QA before the user** — a design QA reviewer passed at least one option, and failing options were fixed or dropped before the user saw them.
6. **User saw it** — the HTML was opened for the user with its path before the choice was asked.
7. **Approved mockup kept** — the picked stage-1 option (and an HTML-kit stage 2) was copied to `mockup_dir` (unless `none`); a stage 2 built in the project's frontend is kept as the code itself and its path is in the UI spec and the build tasks' notes.
8. **Drawn in UI design mode** — visual mockups came from a developer in UI design mode under this gate, never drawn by the leader — not inside brainstorming, not as CSS or JavaScript injected into a running page, not as hand-written HTML; brainstorming showed at most low-fidelity layout or flow sketches.
9. **One content set** — every mockup of one product draws from one content set (names, categories, items, amounts), built from the product's real data where it exists, recorded with the inventory and reused as the seed data; content that does not match what users really see (food photos in a social-media portal) fails.
10. **Self-checked** — the designer's notes hold a per-option result of the §6 checks and the design-QA points, run before handing over.
11. **Taste and platform** — the user's visual references, or the researched products (when the user asked for research) and the chosen mood, are recorded and followed; native-app mockups follow the platform design system and adaptive layouts for every size tier, with nothing that reads as a web page; the palette has primary, accent, semantic and neutral colours with checked contrast.
12. **Redesign starts clean** — for a request that redoes an existing design, the user said what may be kept (default nothing) and the brief carried the ban list; no option reuses a banned palette, font, kit or layout frame.
13. **Rejections change the method** — a round after a rejected one started from the user's references or the reference gallery plus overview boards; after two rejected rounds the stop rule (`DESIGN-21`) ran before anything was drawn, with a fresh designer.
14. **Stage 1 is light** — stage 1 was an HTML kit in `$TEAM_WS/mockups/`, with no framework code, no build, nothing in the app's source tree and no sub-agents.
15. **Distinct and real** — options differ in layout and navigation, not only palette; the desktop width has its own layout instead of the phone layout stretched; no file name, slug or technical key is shown as a title; every screen has one primary action that stands out from the rest.
16. **QA on evidence** — design QA opened a full-size image per width tier × theme of every main screen and listed them; touch targets meet the platform minimum.
17. **Boards before HTML** — the direction was chosen from three static overview boards of the fixed scope (§1a), built in parallel and spread along the unsettled axis, before any HTML mockup was drawn; only the approved direction got HTML.
18. **References used as asked** — a gallery of real screenshots was studied by the designer (with a written note on what makes the strongest ones professional), or the user's own references were used; how to use them (mood, follow one, listed elements) was asked, and the element checklist the user ticked is in the notes; no screens of two references were spliced together.
19. **Calibrated position** — when feedback was vague or swung between extremes, a 3×3 calibration matrix was shown and the user's cell is recorded in the brief.
20. **Compare page** — the HTML mockup has `compare.html` beside the references it used; tone and colour changes were applied as token edits in the kit, not as a new round.
21. **Stop after two rejections** — after two rejected rounds, the rejection review, the calibration matrix and the reference gallery came before any new drawing.
22. **Divergent and not copied** — boards and options recorded their axes; options of a round differ on three or more axes including shape language and layout skeleton; a redesign keeps neither the rejected skeleton nor three or more signature elements of one reference.
23. **Licensed images and fonts** — photos and fonts came from the project, the user, or official open-licence APIs with `CREDITS.md`; no scraping, no faked `User-Agent`; photos of a screen share one grade.
24. **Market study after three rejections** — after a third rejection of one product, the next design came from a written study of market-grade examples by a fresh designer; the user was not asked to choose among references.
25. **Shown after QA** — every round shown to the user had its design QA `PASS` recorded first.
